Global symlink containment fix evidence

Root cause
- Vault containment was lexical only. The engine cleaned and joined server paths
  under the absolute vault root, but it did not inspect existing path
  components with Lstat before scanner reads, pull writes/deletes, or conflict
  file writes. A symlinked file or parent inside the vault could therefore
  route reads, atomic writes, conflict writes, or delete pre-checks outside the
  vault.

Implementation summary
- Added internal/syncagent/vaultfs with:
  - LexicalPath: keeps the existing relative-path, non-absolute, no-.. escape
    behavior.
  - SafePath: returns a vault path only after walking existing path components
    with os.Lstat and rejecting any symlink component or symlink target.
- Engine pull now validates server-driven sync paths with vaultfs.SafePath
  before existence checks, hashing, reads, atomic writes, or deletes.
- Engine exists checks now use os.Lstat so a symlink target is not followed when
  deciding whether a path exists.
- Scanner now skips symlink entries before Info/Open, preventing upload reads
  through symlinked Markdown files or symlinked directories.
- Conflict writes now validate the generated conflict destination with
  vaultfs.SafePath before ReadDir/MkdirAll/write, and skip symlinked existing
  conflict candidates before parsing.
- Policy: symlinked sync paths are rejected/skipped rather than supported.

Residual risks
- This fix rejects symlinked sync paths; users with intentional symlinked notes
  will need to replace them with regular in-vault files.
- The configured vault root itself is not rejected solely for being a symlink;
  the policy applies to sync paths below the configured root.
